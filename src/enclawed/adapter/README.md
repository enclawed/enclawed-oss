# Enclawed adapter kit

The adapter kit is how Enclawed governs an agent CLI that it does not own. Each host gets a thin adapter (codenclawed is the first) that maps the host's specifics onto the kit and declares its host's facts as data; every decision is the kit's.

One rule decides what goes where. **Every security decision lives in Enclawed.** An adapter only translates its host's specifics:

| The adapter owns                                                           | Enclawed (this kit) owns                                         |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Hook wiring: reading the host's hook input, writing the host's hook output | Whether a call may run: allow, ask or deny, and why              |
| The host's settings format and how to inject one session's hooks           | Which repository settings are refused (environment trust)        |
| The approval UI: a prompt the adapter controls, pausing the host           | Which answer approves which call (approval binding)              |
| Starting, pausing and stopping the host process                            | The containment rules and the halt order                         |
| Where the host keeps its login                                             | When the login is erased, and the check that it is gone          |
| The table from host tool names to action kinds                             | What each kind of action needs (history, a person, an allowlist) |

If an adapter passes a conformance test, it should be because of Enclawed, not because of security code the adapter wrote for itself.

## What a host must provide

From the codenclawed paper's portability section (`HostCapabilities` in `types.ts`; `assessHost` in `host.ts` turns a host's capabilities into the gaps its adapter must cover):

- **R1, a blocking pre-tool hook.** Every call (built-in, shell, file, MCP), in the main loop and in subagents, reaches an external program before it runs, and the program can deny it. It must fail closed: a hook that crashes or times out must block the call. Without R1 there is no adapter.
- **R2, a post-tool output rewrite.** The adapter can replace a tool's result before the model reads it. The input cleaner needs it; without it the cleaner cannot remove a hidden instruction.
- **R3, a settings injection channel.** A flag or variable that adds the adapter's hooks for one session, ranked above anything a repository can supply, plus a way to see and refuse hooks and command settings a project adds.
- **R4, an on-disk transcript** with a stable id per call, so the launcher can bind each decision to the real call and detect a call that ran without one.

## Writing an adapter

1. **Map the host's tools to kinds.** For each host tool name, choose an `ActionKind` (`read`, `fetch`, `search`, `session`, `agent`, `fs-write`, `shell`, `mcp`, `skill`, `unknown`), the field that names its targets, and its `policyIds` (the lowercased host name plus the gateway's canonical id, such as `exec`, `write` or `web_fetch`). Anything you are unsure about is `unknown`: the engine treats it as irreversible.

2. **Build the engine once per session or hook process.**

   ```ts
   const engine = new DecisionEngine({
     host: "codex-cli",
     policy, // the framework's Policy (loadPolicyFromJson)
     projectDir,
     home,
     history: { store: new HistoryStore({ limits: policy.history }) },
     protected: { paths: [stateDir, policyFile, auditLog, installDir], prefixes: [] },
     secretPaths: [sessionDir, hostLoginFile],
     audit: auditLogger, // the framework's AuditLogger
     mcp: new McpSession(admission.admitted),
     workflow: profile, // optional: selectWorkflow(...) result; narrows only
     skills: admission.session, // admitSkills(...).session
     // shell: the default is strictShellClassifier (the read-only allowlist)
   });
   ```

3. **Pre-tool hook.** Translate the hook input into a `PreActionEvent` (tool, normalized params, resolved targets, working directory, call id, and whether a person can be asked), then call `engine.preAction(event, prompt)`. `prompt` is your approval UI: show `req.reason` and `req.code`, return what the person typed. Write `answer` and `answerReason` back in the host's format. The record is written before the answer; if it cannot be written, the answer is deny.

4. **Post-tool hook.** Call `engine.postAction(event)` with `modelReads: true` for tools whose results reach the model. When `changed` is true, replace the result with `output` (same shape). Deliver `note` and `notice` out of band (the host's hook-context channel), never inside the result. At session start, deliver `engine.sessionStart(...).context`.

5. **MCP.** At launch, measure each server definition (`mcpDefinitionDigest`, the executable's SHA-256, and for a package-runner definition the integrity of the package it fetched), load records with `signedMcpPinStore(...).load()`, and call `admitMcpServers` (it refuses launch-time package runners that are not pinned by content). Start the admitted servers only through `launchContained` (the `LaunchContainment` seam); with no containment they do not start. Feed every `tools/list` answer to `engine.mcpDefinitions`; on `stop`, stop the session.

6. **Launch.** Before starting the host: `decideRepositoryEnv` over the repository's settings `env` blocks (refuse the launch on any refusal, with `repositoryEnvMessage`); `decideHooks` over every hook the host would run from any scope (refuse on any refusal, with `hooksMessage`); `admitSkills` over the host's skill roots; `selectWorkflow`; `frameworkEnv` for the environment the framework and the host see; `activateSession` for two-factor activation (with an Enclaweder bound: a device-verified code after FIDO2, or one device-counted unlock use for a headless start; `issueDeviceUnlock` makes the grant); `bindHardwareRoot` for the per-call gate. A CI adapter first asks `decideTrigger` whether the event's actor may start a run. Implement `LaunchServices` for the host-specific parts, and follow `HALT_SEQUENCE` on a halt.

7. **Hook transport.** Write the hook's configuration with `writeSessionFile` and put its digest on the hook command line (`emptyEnvCommand` builds the `env -i` form); the hook reads it with `readSessionFile` and `replaceProcessEnv`. On the launcher's control socket: `verifyHookPeer` for each connection (Linux: `linuxPeerLookup`, `linuxProcessProbe`), `HookHandshake` for session start, `CallLedger` (with `contextMatches`) for every reported decision, approval and result. After the session, `reconcile` the audit log against the host's transcripts (the adapter parses its transcript format).

## Rules beyond codenclawed (closure plan)

- **Credential custody (M6).** `./credentials.ts`: the user's credential stores (`~/.aws`, `~/.ssh/id_*`, `~/.netrc`, `~/.docker/config.json`, `~/.kube/config`, gcloud, `~/.npmrc`, `.env` files, `/proc/*/environ`) and environment dumps (`env`, `printenv`, `export -p`, ...) are asked every time (never pre-approved) and refused with no person; credential formats are removed from tool results before the model reads them, and an MCP, fetch or search call carrying one is refused.
- **Project secret files (row 40).** `.env*` (not templates), `credentials.json`, `secrets.yaml`, `.npmrc`, `id_rsa`-style keys, `*.pem`, `*.key`, `*.p12` and the like are credential files wherever they are, the project included: named reads and commands ask every time and are refused with no person.
- **Search and read tool arguments (row 60).** A string argument of a local read or search tool that begins like an option is refused (the host's search program could read it as one); path-named arguments are checked like read targets. An adapter lists in `literalParams` the arguments its host passes as data (after `--` or `-e`).
- **Execution provenance (M5).** `./exec-provenance.ts`: download-and-execute denied; another agent CLI with its checks off denied (on: asked); package installs that run install scripts asked every time; project scripts (`npm test`, `npm run x`, `make t`) resolved and shown in the question.
- **MCP code pinned by content (M2).** `./mcp-package-pins.ts`, `./runner-pins.ts`: `npx`/`npm exec`/`pnpm dlx`/`bunx`/`yarn dlx`/`uvx`/`pipx run`/`uv tool run`/`docker run` definitions start only in an exact form whose content the signed record pins and the launcher measured: npm runners by the lockfile's integrity, a digest of every locked package and the installed tree (pnpm-lock.yaml, bun.lock, npx's package-lock.json; yarn keeps no tree, so npx's install of the same package is measured); Python runners by the wheel hashes the index lists, every installed file against its distribution's RECORD (no unlisted file Python would load), the environment's tree and interpreter, and at pin time the downloaded wheels against the index and the installed RECORD. The measured tree is started; the runner never runs. The caches are found where the runners themselves look (`runnerCacheDirs`: a runner option, the environment, then their config files, `.npmrc`, `pnpm-workspace.yaml` and pnpm's rc, `bunfig.toml`, `.yarnrc.yml`, `uv.toml` / `pyproject.toml [tool.uv]` (none for uvx), with the Linux, macOS and Windows defaults); a location only says where to look, since what is found must match the pin. `uvx --from NAME==X CMD`, `uvx NAME@X` and `pipx run --spec NAME==X CMD` are exact forms. A Python release is checked against the index only at pin time (`pythonIndexUrls`, the wheels downloaded and chained to the installed RECORD); a launch measures the environment against the record's pin and reads no index. yarn dlx keeps no tree, so the adapter installs the release once through npx at pin time (`yarnDlxInstallCommand`: no install scripts) and that tree is measured and started. `uv run` needs a uv.lock and pins the project with its environment (every installed distribution pinned by uv.lock, every file against RECORD, the interpreter's file); it starts the environment's interpreter and entry directly (`localCodeLaunch`; uv never runs; a program from outside the environment is refused). deno needs a lock file (or remote imports off); its cached npm packages, remote modules (the lock's SHA-256) and jsr packages (the metadata's integrity, each cached file's checksum) are measured independently of deno, and deno starts with its lock frozen, its cache only and no V8 or transpile cache. `python -m` checks the distribution's files against RECORD. Tree digests reuse a file's hash only while its stat identity (device, inode, size, modification and change time) is unchanged (`treeHashCache`, in the adapter's protected state; refreshed with a full rehash at pin time), so large environments (up to an internal bound of a million files) can be pinned.
- **MCP argument roles (M4).** `./mcp-roles.ts`: roles signed in the record (`git-rev`, `positional`, `path-ro`, `path-rw`, `url`, `opaque`), checked before the call; role maps for the reference servers.
- **Hooks in every scope (M7).** `decideHooks` in `./env-trust.ts`: user, plugin, `--settings` and repository hooks start only when granted by digest (the digest covers the scripts they name).
- **Who may start a run (M8).** `./trigger.ts`: an explicit allowlist of principals by platform id; bots and apps only by app id, never by a `[bot]` name.
- **Containment (M1/M3).** `./contained-launch.ts`, on the framework's `../containment`: an MCP server starts only through `launchMcpServer` with the containment part of its signed admission record (`McpAdmissionRecord.containment`, inside the signature); no record is `mcp-server-not-contained`, a machine that cannot contain is `containment-unavailable`. The definition's working directory (`cwd`, absolute: a server that starts in its project, `python -m`, `uv run --directory`) is passed to the containment, which refuses one outside the record's roots and package root (`containment-cwd-outside-roots`). Every `tools/call` goes through `bracketMcpCall`. Project scripts and package installs the agent runs are marked by the engine (`Decision.contain`) and run only as the command the session's `ScriptContainer` (`scriptContainer`) returns (`HandledDecision.rewrite`; the adapter replaces the host's input with `rewrite.params`); with no container they are refused. `enclawedLaunchContainment` implements the `LaunchContainment` seam for what the launcher starts itself.
- **Host environment (M6).** `hostEnvironment`: the host starts with the framework's variables, the names it declares and credential handles bound to destinations, nothing else from the shell. The engine (`credentials` option) refuses a handle's value sent anywhere else, asks for a command that names the handle's variable, and removes the value from results.
- **Project secret files in search results (M6).** Every model-read result loses the lines a search labels with a secret file's path and the values the project's secret files hold (`./project-secrets.ts`); plain values (`PORT=3000`) stay.
- **Network-origin taint (M5).** `./exec-taint.ts`: a file one command downloads, run by a later command, is download-and-execute (`taint` option; `fileTaintStore` when every hook is its own process). The taint follows the bytes: unpacking a downloaded archive taints its members (listed from the archive; the destination written since when it cannot be listed), mv/cp/install/ln/rsync/dd, `cat x > y` and decompression taint the target, a downloaded stream piped on stays tainted, and running any file whose content digest is a download's is download-and-execute whatever its path. A vendored archive nobody downloaded taints nothing.
- **Local code and the host CLI by content (M2).** `./code-pins.ts`: `node script.js`-style servers by the tree of the script's package, `python -m module` by the module's files and its distribution's files, installed scripts through what they run (`measureLocalCode`, checked in `admitMcpServers`); `measureHostBinary` + `admitHost` pin the host agent CLI.
- **Provider switches.** A repository's provider switch, region or Vertex project id with an on/off, region or project value is class `provider`: started and recorded (`accepted`). An endpoint, a URL, a credential or a gateway is refused as before.
- **Key files by content.** `.key` and `.asc` are credentials only when the content has a private key's shape (or in `/etc/ssl/private`); a Keynote document is not.
- **Per-call skill conformance.** `./skill-conformance.ts`: a shell call made under a verified skill (it executes a file whose real path is inside a skill of the session's verified set, and that file's sha256 and the skill directory's content digest still equal the admission's) is decided against the skill's admitted capabilities by rule. It conforms when it is that one simple command (no list, pipe, redirection, expansion, assignment or wrapper), runs an analyzed script (.py, .sh, .bash, .js, .mjs, .cjs, outside dot-directories and node_modules) under its language's interpreter (no interpreter option; run directly only with a plain shebang naming it), every URL argument falls inside the skill's declared `enclawed-egress` targets and every path argument and the working directory inside the skill or, with an fs capability, the project. Conforming: allowed with no person (`skill-conformant`; irreversible capabilities add `executed-under-skill` and the audit record names the skill), run contained by `scriptContainer` from a private copy whose digest is checked again (`skill-changed` otherwise) with exactly the skill's capabilities (project read-only or read-write, programs by `spawn.proc`, the network only to its targets through the relay with their request shapes). Not conforming: denied (`skill-nonconformant`), never asked. A skill whose files changed, or a `SkillSet` without the admission facts (`contentDigest`, `files`, `caps`), is not attributed: its calls keep the ordinary rules. Pass `admitSkills(...).session` as `skills`, and a `ScriptContainer`, for this to apply.
- **Request shapes of destinations (egress profiles).** A net.egress target is scheme, host, port and an optional request shape (`../egress-target.ts`: `https://registry.npmjs.org:443#npm-registry`; a bare host still parses as before). Skills declare them in `enclawed-egress`. Containment destinations take `shape` (`../containment/request-shape.ts`: `npm-registry`, `pypi`, a `pathPrefix` for Artifactory-style proxies, artifact `pins`): only that protocol's metadata and artifact fetches reach the destination, a pinned artifact is verified before the process sees it, and everything else is refused (403 and an event). Package installs use the registry shape by default (`registryDestinations`; a mirror given as a URL keeps its path as the prefix).
- **MCP tools read-only by the signed record.** An MCP call runs with no person when the server's signed admission record contains it with only read-only folders, no network destination, no secret and no writable configuration (`mcp-contained-read-only`), after the argument-role and outbound-credential rules; the server's own tool annotations are never read for this.
- **Skill admission reads the libraries a skill runs.** Method A (`enclawed/src/skill-formal-static.mjs`) analyzes every file the skill's content digest pins: node_modules, vendored site-packages-style trees and dot-directories included; a file it cannot read (a compiled extension, an unknown language, an executable without a known shebang, a .git directory) refuses the skill. It also reads: shell file tools (cat/head/grep... read; tee/cp/install/touch/mkdir/ln and sed -i write; dd/truncate/chmod irreversible; ssh/scp/rsync and /dev/tcp reach the network; sourcing a file named by a variable is TOP), fs functions imported by name, Python writes with a computed path or mode, database queries (a literal read-only statement reads, a literal write writes, DDL changes the schema, a query the code builds can do all three), and deserialization into live objects (a class taken from a map and constructed, Reflect.construct, unserialize, pickle/dill/marshal, yaml.load without SafeLoader, a computed getattr or importlib.import_module) as TOP. `enclawed-write-roots` in SKILL.md declares the folders a skill writes; every write must then name a literal path inside one (a computed path can leave them, CVE-2026-27825 shape). A bundle signed before stays valid while the fresh analysis of its skill is unchanged; a skill the new reading changes is drifted and must be signed again.
- **Skill admission counts every use, not only the listed entry points.** The biconditional at signing and at every launch also takes the second pass of Method A (`enclawed/src/skill-formal-uses.mjs`, `skill-formal-shell.mjs`): every simple command a shell script runs (in lists, pipelines, subshells, substitutions, unquoted here-documents, if/while/for/case bodies, behind env/nohup/timeout/nice/xargs) is classified by a table of programs and their arguments (every rm/mv operand, find -delete and -exec, git by subcommand, sed and awk scripts that run or write, an interpreter with inline code), and every module Python or JavaScript code imports is classified, member by member for the ones that reach the system (os, shutil, subprocess, pathlib, tempfile, io, fs under any name, fs.promises, child_process), with the command line a spawn starts read as shell. A program, module or member it does not know, a command word or spawned program the code computes, a module that is not a file of the skill, or a way around the module system (process.binding, globalThis[...], createRequire) cannot be bounded and refuses the skill; its writes are held to `enclawed-write-roots` like Method A's. Before it, `find -delete`, `git clean`, `perl -e`, `from shutil import rmtree`, `import { execSync } from "node:child_process"` or `os.system("rm ...")` produced no effect, so a skill declaring `[fs.read, fs.write.rev]` could delete with no person. The framework's own bundle evidence (`methodA`) is unchanged; a signed skill the second pass refuses fails verification at its next launch (`failed`, with the reason).
- **Contained execution.** `./contained-exec.ts`: a command line that is not read-only but runs only code Enclawed reads (node scripts, `node --test` and its test files with their relative imports, `-e` code, python scripts, `-m pytest`/`unittest`, `-c` code, sh/bash scripts and `-c` lines read again by the same rules, `source`, a project file run by its shebang, and npm/pnpm/yarn/bun `test` / `run X` when package.json equals git's committed copy), with nothing containment cannot take back in that code (the network, other programs, deleting or renaming files, run-time code loading, a path outside the project) and no assignment that changes what commands run (except clearing one), runs with no person, even headless: every project file git does not hold as it is now is snapshotted into history first, and the command runs only as the session's `ScriptContainer` rewrites it (`contain.kind` "project-script": the project read-write, nothing else of the machine, no credentials, the network only to declared destinations, exec-config files refused). With no container, or when anything does not read clean, the old rule applies and the question says why. `repositoryEnv` (engine option): the variables the repository's own settings set that change what commands run (NODE_OPTIONS, ...), even when the host pins them; while set, a runner must set or clear each itself. `sed -i` with a text-editing script is decided as the equivalent Edit of its files (`in-place-edit`).
- **Secrets by content.** `./secret-content.ts`: a file anywhere (the project included) that holds a credential format the framework's DLP scanner knows, a provider key format (Stripe, OpenAI/Anthropic, Slack, GitHub, GitLab, npm, PyPI, Hugging Face, Google, JWT, DigitalOcean, SendGrid, Shopify), a private key block, or, when its name says token/secret/credential/password/api key/auth, nothing but one to three token-shaped values, is a credential: a read of it, or a command that prints it, asks every time and is refused with no person (`credential-path`); `wc` (counts only) and listings do not show it. The provider formats are also removed from results and refused in outbound arguments.
- **Command lines read exactly.** `./shell-compound.ts`: a POSIX line is read as the simple commands the shell will run: lists (`;`, `&&`, `||`, newlines), pipelines, redirections that change nothing (a descriptor onto another, anything to or from /dev/null), and the expansions whose value is known (`~`, `$HOME`, `$PWD`); command and process substitution, other variables, subshells, groups, background jobs, here-documents and other redirections are refused. Each command carries every directory it may run in (`cd` followed; a `cd` that may fail leaves the commands after `;` or `||` possibly where they were), and the secret, credential and protected-path rules check each command there. A line is read-only when every command in it is on the strict allowlist with no assignment in front. A command that only lists names (ls, stat, a read-only find) reads no credential's content.
- **Git configuration by what each command starts.** `./git-programs.ts`: the repository's config (by section) and its hooks directory give the programs git can start (fsmonitor, clean/smudge filters, textconv, external diff and diff drivers, a post-index-change hook, pager, gpg, includes); a read-only git command asks only when it actually starts one, as measured on git v2.53.0 (`git ls-files` starts core.fsmonitor; `git log` without a patch starts no textconv; `git status` runs a post-index-change hook even with no config line).
- **Ignored files are overwritable.** Overwriting a file git ignores (regenerable output) needs no person; credential files excepted. Untracked, not ignored, files still ask.
- **The window between a decision and the run.** `./action-scope.ts`, `./file-integrity.ts`: every call the engine allows opens a checked action in the file-integrity record with the scope its decision gives (`auditedActionScope`): what it may change (nothing for a read-only command, a read, a person-named fetch or a new temporary file; exactly the targets of a redirect or in-place edit; anything for contained execution, a pre-approved call, MCP tools and skills) and what it reads (every word of every simple command where it runs, globs as their directory, input files, the working directory for tree readers, the whole project for git; the named paths of a read tool). A change while it runs outside its write scope is never its own: it is recorded as a change outside the agent (`file-changed-outside-agent`, the exec variant for links and executables), audited, and the watcher is not held back for it. When such a path is in the call's read set, `postAction` withholds the call's whole output from the model (`tool.output-withheld`), so a file swapped for a link to a credential store, or given a secret, between the check and the read never reaches the model, whatever its name. At decision time a path that resolves into a credential store is that store; the output cleaner also removes credential-shaped assignments by content (`redactSecretAssignments`) and the values of any secret a link in the project reaches.
- **Which file a command word runs.** `./program-path.ts`: an allowlisted name is the allowlisted program only when the session's PATH (`environment.PATH`, else the hook's own) resolves it, first match as the shell does, in an absolute directory that is neither in the project, a temporary directory nor a scratch path, to a file there too, both writable by no one but the system or this user. A planted `ls` or `git` earlier on PATH, a relative or empty PATH entry, a `PATH=` assignment on the line, and the programs xargs, nice, timeout or find -exec start are decided as unverified programs (`shell:program-unverified`: contained, or asked).
- **Aliases and functions of the host's shell.** `./shell-definitions.ts`, engine option `shellDefinitions` (the aliases, name to text, and the function names of the shell the agent's commands run in; the kit adds the functions `environment` exports as `BASH_FUNC_NAME%%`): a simple command whose command word is a function (quoted or not), an alias (unquoted literal words only: `\ls` and `'ls'` skip aliases), or any word while an alias names a reserved word or `command_not_found_handle` is defined, is decided as an unverified program, with the alias text or function named in the reason; `ls='ls --color=auto'` (the same name with only `--color` options, still read-only with them) is the same program. `unalias` or `unset -f` on the same line removes nothing. Absent, null or `"unknown"`: every command word is unverified. A contained command reaches its containment through the host's shell (`exec env -i ...`, `containedCommandLine`): containment is not offered when `exec` may be defined, and a container's returned line whose command word is defined is refused (`shell-definition-shadow`). Conformance `shell-definition-shadow`.
- **URLs the person named.** `./person-urls.ts`, engine option `personUrls`: the http(s) URLs in the person's own task text (`personUrlsOf` over the host's prompt argument or its user-prompt event; never a file, a tool result or model output), WHATWG-normalized, fragment dropped. Needs no person (`person-named-url`), open flavor only (an enforced host allowlist is never widened): a WebFetch of exactly one of them; a shell line whose GET is `curl` (quiet, fail, follow, verbose, timeout options and `-o FILE`; no data, header, method, upload, config file or URL glob), `wget` with `-O` (`-O-` or a file), or `python3 -I -c` code whose one reach beyond a pure filter is `urllib.request.urlopen('URL')` of that literal URL (`./pure-code.ts isPythonGetOf`), and whose other commands are read-only, pure filters (tr, sed substituting or printing, `python3 -I -c` pure-filter code), or `mkdir` in the system's temporary directory, with every file written (the output file, a `>` redirection) a new file there outside the home, the project and the secrets. Also: `node -e` code that is, read as a syntax tree (acorn), exactly a promise chain on one `fetch('URL')` of the literal URL (only then/catch/text/json, console.log/error, arrow functions with identifier parameters and expression bodies, members by name; no computed member, no other name), with the session's environment known and no NODE_OPTIONS (`./pure-code.ts isNodeGetOf`); Python run with `-c`, a here-document or a script file whose code is the urlopen GET, without `-I` only when every import can load only the standard library (`./python-run.ts`: no module file or package named as a standard-library module or as one the code imports in the first path entry, no PYTHON\* variable in the known environment, no `usercustomize` or `.pth` in the user's site-packages); and the bash idiom `exec N<>/dev/tcp/HOST/PORT; printf 'GET PATH HTTP/1.x\r\nHost: …\r\n\r\n' >&N; cat <&N` with nothing but that request line, Host and Connection: close (`isPersonNamedDevTcpGet`).
- **Pure filters.** `./pure-code.ts`: `python3 -I -c CODE` whose code imports only pure modules (sys, re, html, json, collections, unicodedata, string, math, itertools, base64, binascii, textwrap, statistics), uses no double-underscore name anywhere, no file/introspection/code builtin and only sys's streams, argv and exit, reads its input as data: piped from a download it is not download-and-execute (`./exec-provenance.ts`). sed with one substitute or print script (no w, e, r, R, W; no -i) and tr are filters.
- **Environment prints on the session's environment.** `./env-filter.ts`, engine option `environment` (the environment the agent's shell commands run with: the adapter's hook process's environment, which is what the host hands its shell): `env` or `printenv` piped straight into `grep [-i|-w|-F|-E] WORD` needs no person when no line the grep keeps holds a credential (a credential-shaped name, a known credential format, a provider token or a token-shaped value; absolute paths are locations). A later `sed 's/=.*/X/'` or `cut -d= -f1` leaves only names. Without `environment`, every print asks.
- **Reads of a directory.** A path argument of a read tool descends below the path only as the host lists it among the call's reads (`recursive`); a Read of a directory that holds a secret path deeper down lists names and reads no secret. A path the host did not list may descend (the wider set).
- **Listings and absent credentials.** A `find` whose expression can never print a file does not list it for the reader that takes its names (`./find-expr.ts`, a superset of find's evaluation). A credential path under the command's directory or the home directory that does not exist (ENOENT) shows nothing, when nothing earlier on the line can create a file (only read-only commands, git only when the repository makes it start no program); system credential locations keep the rule by name. grep's pattern operand is not a file, and a glob is expanded only as a whole shell word.
- **Commands that name a credential but show none of it.** echo/printf (their words), `du` (sizes), `test`/`[` with file tests only (metadata), `cut -d= -f1` over environment files whose every line is an assignment, and `grep -o` with a pattern matching only name characters and `=` do not reach the credential they name; a credential path that does not exist shows nothing; a glob is decided by the files it matches now (each read as if named, by name and by content; too many to check is a hit), and below its static prefix only for a reader that descends.
- **Reading an unverified skill's files.** A shell command the strict classifier proves read-only may name files under a skill directory that is not in the verified set (it runs nothing there); anything else naming such a directory is still denied (`skill-not-verified`).
- **New files in the system's temporary directory.** A write that creates a file (nothing at the name, no link) under the system's temporary directory, outside the home directory, the project and the secret paths, is scratch (`temp-new-file`): removing it undoes it. Exec-config, protected and linked targets are decided first.

## Containment v2 seams and adapter conformance

- **tools/call** goes through `bracketMcpCall`, which is the containment's `runCall`: one call in flight per server (two at once would be `call-ambiguous` at the relay).
- **Package installs** run only as `containPackageInstall` (caged: outputs, lockfiles and manifest dependency fields; the registry only). `ContainedLaunch.tool` names the package manager; project-policy hosts never apply to installs.
- **Remote MCP servers** (type http / sse) connect through `connectRemoteMcpServer` with the `remote` part of the signed record (url, transport, authorization origins, optional `oauth` client id and scope); every call body goes through Enclawed's egress pipeline first (with no runner given, every stage registered for tool calls). No `mcp-remote` bridge. OAuth (`./remote-auth.ts` `authorizeRemoteMcpServer`): the signed client id or dynamic client registration (RFC 7591), PKCE S256, a loopback redirect that accepts only this request's state and issuer (RFC 9207), the URL shown to the person (never opened), every endpoint under the containment's origin rule, no redirect followed. Tokens and secret header values live in Enclawed's credential store (`remoteCredentialStore`, bound to the server's URL and origin, sealed at rest with `credentialStoreKeys`: a key the bound Enclaweder derives, else one in the OS keyring (`osKeyring`), else a 0600 key file in the adapter's protected state apart from the records) and reach the server only through the remote client's `requestHeaders` seam (`remoteCredentials`): an expired token is refreshed, a refused refresh token is dropped, and no answer carries a credential's value. `probeRemoteMcpServer` reads a server's identity and tools once, for pinning.
- **A held conflict without a launcher prompt.** With the engine's `conflictGrants`, the one write of a conflicted repository-configuration file (still the reported content, a single-link regular file, a person to ask) is asked at the host's own prompt, only in a mode the adapter declares person-held (`ConflictGrants.personModes`, host data: a mode in which a mode switch while the prompt is open would let the host approve the pending write by itself is not one), with a grant in the file-backed `ApprovalGrantLedger` (bound to the path, the file, the conflicted content and the call); every other call stays denied. `completeConflictResolution` spends the grant on the host's post-tool event for that call and admits the file again (`handleRepoConfigEvent`, state "resolved"); a call the host ran in another mode is not an answer: the file goes to the adapter's quarantine and the session stays held.
- **Asks at the host's own prompt.** With no adapter prompt (the engine's `hostPrompt`, a `HostPromptGuard`), an "ask" goes to the host's permission prompt, which may approve a pending call by itself: a host may re-run its own permission check, without the hook, whenever its permission context changes while the prompt is open (a mode switch), and run the call when that check allows it. The adapter declares as host data what its host's check can allow by itself (`HostSelfApproval`: person-held modes, the action kinds it allows in any mode and those it allows only outside a person-held mode, shell command prefixes, preapproved fetch hosts, the tools its allow rules name); `hostSelfApproval` decides per call: never, only in another mode, or in any mode. A call the host cannot approve by itself is asked there as usual. One it can approve only outside a person-held mode is asked only when it is a write Enclawed can put back (an untracked overwrite whose prior content is snapshotted) and only in a person-held mode, with a per-call grant (`askAtHostPrompt`); every other such ask is denied up front (`host-self-approval`). On the host's post-tool event (`PostActionEvent.hostMode`) the engine spends the grant (`completeHostPromptAsk`): a call that ran in another mode, or with another input, is `approval-not-from-person`: the write is quarantined, the file is put back from its snapshot, the record is written, and the host session is held (`hostPromptHold`; every later call is denied). `hostPromptAnswerer` decides over the host's managed settings whether anything but the person can answer the prompt (the hook lock, answering hooks, enabled plugins, pinned settings); when something can, every ask is denied (`host-prompt-answerable`).
- **The order of the host's modes.** The adapter declares how permissive its host's permission modes are (`HostModeOrder`: a rank per mode, pairs where a lower rank still allows something the higher one does not, the narrowest mode of a rank, the plan and bypass modes, whether plan runs as bypass when bypass is available, and the modes in which no person answers an ask); `compareHostMode` decides same, narrower or not within. The headless mode binding (`contextMatches`, `LaunchContext.modeOrder`) accepts a mode narrower than the launched one (the host fell back by itself: a host may start a session in its default mode when the launched mode is unavailable for the model, the account or the settings) and reports it (`ContextCheck.downgraded`, `CallLedger.downgrades`) for the adapter to record as `host-mode-downgraded`; a wider or incomparable mode stays a `context-mismatch`, and so does a mode in which a person answers an ask under a launch mode in which nobody does (`noPersonModes`, such as a mode that skips every prompt: the kit denies an ask there, and the downgrade would turn that denial back into an ask). The same order decides which declared person modes count (`isPersonHeldMode`, `HostSelfApproval.modeOrder`, `ConflictGrants.modeOrder`): only the narrowest prompting rank, never the plan mode.
- **Containment events** become audit records with `containmentAuditOf` (closed types: view-changed, original-restored / not-restored, install-cage, egress-allowed / egress-refused with the relay code).
- **Account connectors** (no server to pin): `new McpSession(admitted, { connectors, connectorServer })` admits only the tools the operator's policy lists.
- **Adapter conformance:** `enclawed conformance --adapter <module>` runs the adapter invariants (`conformance/checks-adapter.ts`) through the adapter's own event mapping; the module exports `enclawedConformanceAdapter { host, decide(intent, sandbox) }`. A kit whose decision is stubbed to "allow" fails every attack case.
